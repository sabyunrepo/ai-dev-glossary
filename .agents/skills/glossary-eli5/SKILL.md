# 쉬운 용어집 편집

이 스킬은 이 저장소의 `terms.js`, `index.html`, `styles.css`에 적용한다. 대상은 개발을 모르는 성인이다. ELI5는 배경지식이 없어도 이해하는 설명이며, 어린이 말투를 뜻하지 않는다.

## 시작할 때

- 저장소 루트의 `AGENTS.md`와 `terms.js`에서 관련 용어를 읽는다.
- `terms.js`가 설명의 원본이다. HTML에 용어별 글을 중복해서 적지 않는다.
- 새 항목은 기존 ID를 바꾸지 않고 다음 빈 ID를 쓴다. 기존 링크의 `#t33` 같은 주소를 유지한다.
- 새 용어와 중복되는 항목이 있는지 이름·별칭을 확인한다. 관련 용어에는 실제 존재하며 이해에 도움이 되는 ID만 넣는다.
- 분야는 기존의 비슷한 용어를 기준으로 고른다. 예를 들어 문서 표기는 `문서·파일`, 서비스 간 연결·저장·인증은 `웹 서비스`, AI 작업 기능은 `AI 도구`가 기본이다. 새 분야는 기존 분야로 설명하기 어려울 때만 만든다.

## 한 용어의 글쓰기

하나씩 아래 필드를 채운다. 글자 수는 짧게 쓰는 목표이며, 정확성을 위해 필요한 설명을 억지로 자르지 않는다.

| 필드 | 작성 기준 |
| --- | --- |
| `id`, `term`, `aliases`, `category` | 안정적인 ID, 공식 이름, 검색할 다른 이름, 기존 분야 |
| `short` | 하는 일을 한 문장으로. 가능한 30~65자 안팎 |
| `analogy` | 익숙한 장면 하나로 핵심 관계를 설명. 짧은 1~2문장 |
| `example` | 실제로 만나는 사용 장면 하나. 한 문장 |
| `note` | 비유의 한계나 흔한 오해 한 가지. ‘알아두면 좋아요’에 항상 표시됨 |
| `emoji` | 이 용어를 떠올릴 만한 이모지 하나. 큰 제목 그림으로 표시됨 |
| `analogyEmoji` | 비유 속 익숙한 물건·장면 하나. 예: 주소 쪽지 → 🛵 |
| `related` | 이 용어 다음에 이해하면 좋은 기존 용어 ID 배열 |
| `sources` (선택) | 제품 기능·변경 가능한 정보에 대한 공식 자료. `{label, url}` 배열이며 ‘알아두면 좋아요’ 안에 표시됨 |

비유를 쓰기 전에 ‘누가 무엇을 받아 어떤 일을 하는가’가 실제 개념과 맞는지 확인한다. 비유를 이해하는 데 또 다른 개발 용어가 필요하면 다시 고른다. 정의를 조금 바꿔 비유처럼 반복하지 않는다. 예를 들어 환경변수는 배달 주소 쪽지에 빗댈 수 있지만, 주소 이외의 값도 담는다는 사실은 유지한다.

여러 항목은 5~7개씩 다듬은 뒤 전체 흐름을 확인한다. 문장 패턴을 억지로 통일하거나, 모든 용어에 같은 로봇·도구 이모지를 반복하지 않는다. 제품 이름·설정 형식이 관련되면 공식 자료를 확인한다. 특정 제품 기능과 일반 개념을 구별하고, 제품별로 다른 동작을 보편 규칙처럼 쓰지 않는다.

## 실제 파일이나 코드가 도움이 될 때

파일·작성 규칙·코드의 생김새를 보면 이해가 쉬워지는 항목에만 `formatExample`을 넣는다. AI, 머신러닝 같은 개념에 억지 JSON을 추가하지 않는다.

```json
{
  "label": "앱 설정 쪽지 예시",
  "language": ".env",
  "code": "# 연결할 곳을 적어요\nAPP_URL=https://example.com",
  "note": "주소는 예시예요. 실제로 쓸 때는 앱이 이 값을 읽도록 준비해야 해요.",
  "annotations": [
    {"code": "APP_URL", "text": "앱이 찾는 이름표예요."},
    {"code": "= 뒤의 주소", "text": "그 이름표에 적힌 내용이에요."}
  ]
}
```

- 보통 3~10줄의 작고 실제적인 예시로 시작한다. 전체 파일인지 일부인지 밝힌다.
- JSON은 그대로 파싱 가능하게 쓴다. JSON 안에 주석이나 뒤쪽 쉼표를 넣지 않는다.
- Markdown은 표준 전용 주석이 없으므로 `annotations`로 설명한다. HTML 주석을 Markdown의 고유 문법처럼 가르치지 않는다.
- `.env`·Shell의 `#`, HTML의 `<!-- -->`, CSS의 `/* */`, JavaScript의 `//`, SQL의 `--` 등 해당 형식이 지원하는 주석만 쓴다.
- 주석은 ‘무엇을 하려는 줄인지’를 쉬운 말로 설명한다. `annotations`는 이름표·값·결과를 짧게 풀어준다. 코드 안 이모지는 필수가 아니다.
- 가짜 주소·키·비밀번호임을 밝힌다. 실제 비밀값을 샘플에 넣지 않는다. `.env`는 환경변수를 전달하는 방법 중 하나이며, 파일만 만들면 모든 앱이 자동으로 읽는다고 설명하지 않는다.
- 제품 설정·MCP·Plugin의 가상 규격을 만들어 실제 예시라고 쓰지 않는다. 확인 가능한 형식을 쓰거나 파일 예시를 생략한다.

## 모바일 읽기 화면 유지

`index.html`은 `emoji`, `analogyEmoji`, 설명, 사용 장면, 작성 예시, 관련 용어를 표시한다. `styles.css`의 큰 글씨·넓은 간격을 유지한다.

- 모바일은 한 열, 짧은 뜻 → 비유 → 사용 장면 순서다.
- 제목 이모지는 76~104px, 비유·사용 예시 본문은 20px 이상이 현재 기본값이다.
- ‘실제 작성 모습’, 그 안의 줄별 해설, ‘알아두면 좋아요’는 접기 버튼 없이 항상 표시한다. 넓은 간격과 짧은 문장으로 읽기 편하게 유지한다.
- 코드의 긴 줄은 화면 안에서 감싸고, 컨트롤은 누를 수 있는 충분한 크기로 둔다.
- 관련 용어 연결, 검색, 분야 필터, 추천 순서, 이전·다음 이동을 보존한다.

## 용어 설명 그림

설명 그림은 따뜻한 바탕·부드러운 클레이 질감·큰 그림·짧은 한글 이름표가 현재 승인된 스타일이다. 용어마다 비교, 순서, 확대, 내부 모습 등 핵심 관계가 잘 보이는 구도를 고른다. 한 그림에 비유 하나만 담고, 그림만 보고도 누가 무엇을 받아 어떤 일이 일어나는지 알 수 있게 한다. 많은 문장이나 장식으로 채우지 않는다.

- 새 래스터 그림은 imagegen 스킬에 따라 생성하고, 개념의 정확성·한글·화살표 방향·잘림을 직접 확인한다. 첫 환경변수 그림의 ‘주소 설정’ 구도를 다른 개념에 일괄 적용하지 않는다.
- 게시용 파일은 `assets/illustrations/tNN.webp`에 둔다. 생성 원본과 제작 프롬프트는 `output/imagegen/`에 보관하며, 이 폴더를 무조건 공개 저장소에 추가하지 않는다.
- 용어에 `illustration: {src, alt, width, height}`를 넣는다. `alt`는 제목을 반복하는 대신 그림의 관계를 쉬운 한국어로 설명한다. `width`·`height`는 원본의 실제 크기다.
- 그림은 읽기 화면에서만 크게 표시한다. 검색 목록에 모든 원본을 한꺼번에 불러오지 않는다. 그림 아래의 뜻·비유·실제 예시와 관련 링크를 보존한다.
- 새 용어의 그림이 아직 없으면 그림 필드를 생략해도 글은 정상적으로 표시된다. 없는 파일을 임시 경로로 연결하지 않는다. 새 스타일로 바꾸거나 전체 이미지를 재생성할 때는 현재 사용자의 요청 범위를 따른다.

## 확인과 완료

저장소 루트에서 실행한다.

```sh
node .agents/skills/glossary-eli5/scripts/validate-glossary.mjs
```

검사는 필드·ID·관련 링크·JSON 예시를 확인한다. 비유가 쉬운지와 정확한지는 별도로 읽고 판단한다. 새 UI나 긴 예시를 추가했다면 모바일 좁은 화면과 큰 화면에서 잘림·펼치기·검색·관련 용어 이동을 확인한다.

한 항목을 임시 JSON 초안으로만 만들었다면 먼저 JSON 문법을 확인한다. 사이트에 실제 반영할 때 기존 배열에 합친 뒤 위 명령을 실행해야 ID 중복과 관련 링크까지 검사할 수 있다.

`terms.js` 내용을 바꾼 뒤에는 `index.html`의 스크립트 버전 쿼리도 갱신해 예전 설명이 캐시에 남지 않게 한다. 공개 배포는 현재 사용자의 요청이나 기존 승인 범위에 따르며, 이 스킬 자체가 배포를 허가하지는 않는다.
